# Daily post-game chat

A Nostr identity (including the automatically generated anonymous session key) and a server-verified private completion unlock the matching room among today and yesterday, for wins and exhausted guesses alike. Public score posts alone do not qualify. The existing completion validator recomputes outcomes from signed ordered guesses; this is casual spoiler protection, not proof that someone played without assistance.

The browser calls same-origin `POST api/chat/rooms`, `read`, and `send`. These requests are signed kind 30078 events with the sole schema tag `word5.chat.v1`, a matching action, and a random 128-bit nonce. Nothing is published to Nostr relays. New clients request `rooms` with signed `includePrevious:true`; it returns only independently completed current/yesterday rooms, newest first. Legacy callers without the flag continue receiving at most the current room and its original next-rollover expiry. Yesterday never requires completing today, and neither room reveals its word or key without that room’s verified completion. Identity changes clear cached keys and displayed messages.

Each UTC puzzle period has one random 256-bit AES-GCM key, separate from Nostr identity keys. Browser encryption uses a fresh 96-bit IV and authenticates the schema, period, sender public key, and nonce as additional data. The server stores signed ciphertext events. Readers verify the sender signature and event hash before decryption and render text through `textContent`.

Keys are stored in browser sessionStorage under the signing identity. The server retains its shared key in SQLite; it can decrypt messages, and recipients can share their key or retain copies. This is the accepted casual privacy boundary. Do not describe it as encryption that hides content from the server.

New-client access expires at `(period + 2) * PERIOD_MS`: a puzzle is available only while it is today or yesterday, and the yesterday room closes at the next UTC rollover (08:00 Perth). Server physical deletion is separate: keys and ciphertext rows are purged exactly 25 hours after that puzzle ends, `(period + 1) * PERIOD_MS + 25 hours`. Thus an inaccessible two-days-old room can remain stored for its final one-hour deletion grace; it is never listed/read/sent during that interval. Startup, API access and the idle prune timer enforce deletion. Completion records remain score history and cannot recreate an inaccessible room. Previously deleted keys/messages cannot be reconstructed.

The web exposes exactly Today’s chat and See yesterday’s chat controls. Each room has separate ciphertext cache, cursor, result metadata and in-memory draft under the account/period/key binding. Reload preserves a valid selected period but never persists plaintext drafts. Switching cancels only that room’s matching Amber approval; late network, profile, decrypt and signer results cannot mutate another selection. A Today approval may remain valid when its room becomes Yesterday during its 60-second freshness window. At the selected room’s final access rollover, its keys, cache, draft, nodes and matching pending approval are cleared before other cache pruning.

Authenticated `read` responses add `results`, keyed by retained message author, with strict `{period, won, attempts}` metadata from that room’s verified submission. Attempts are integers 1–6; a loss is `{won:false, attempts:6}`. Unchanged delta reads still return room result metadata. The public history API is unchanged, and yesterday badges never use today’s `currentResult`.

Limits: 200 messages per room, 2000 UTF-8 plaintext bytes in the browser, 4096 ciphertext base64 characters, 8000 request bytes read with a bounded stream, 40 signed requests per identity per minute, and 10 sends per minute with at least two seconds between sends. Signatures must be within 60 seconds; accepted request IDs are retained for 120 seconds to reject replay across restarts. Rate records contain no keys, message plaintext, or membership. Session, NIP-07 and bunker identities poll reads every ten seconds. Amber uses the explicit Refresh messages button instead of automatic background signing prompts. Opening chat and sending messages still require signer approval. Amber full-document callbacks resume the exact staged request (including nonce, timestamp and encrypted send payload) for the same identity, selected room period and room-key fingerprint. Only ciphertext is staged; plaintext drafts are never persisted. Approvals older than the server’s 60-second window are discarded and the UI offers an explicit fresh retry. Cancellation clears only that operation’s staging, so an older response cannot remove a newer request.

## Current-room cache and incremental reads

The web client retains at most 200 signed ciphertext events in session storage under the active identity, UTC period and room-key fingerprint. Decrypted text stays in memory/DOM. The same tab can restore either of its previously authorized today/yesterday rooms and verify/decrypt the cached events if the chat API is temporarily unreachable; it does not restore another account or a room older than yesterday. Daily rollover and account changes remove the message cache along with room state. A room-key change invalidates the old cache.

Signed `read` requests may include `after`, the last server cursor event ID. Responses retain `messages` and add `cursor` (newest retained event ID or null) and `reset`. With a retained same-room anchor, only later receipt-order events are returned; an unchanged room returns an empty array. A missing/pruned anchor returns the current bounded snapshot with `reset:true`. Requests without `after` remain full reads, and older servers without cursor fields remain compatible. Clients reconcile full snapshots while reusing already verified/decrypted records and DOM nodes. Sender-created timestamps never control the cursor order.

Refreshing does not clear an already authorized conversation or draft while a network request runs. Transient fetch failures keep cached messages visible, show reconnect guidance and back off background reads up to one minute. Successful reads clear the stale failure notice. Optional metadata failures remain separate from message delivery. This does not claim to diagnose every browser or network cause of a fetch error.

`test/browser-chat-cache.smoke.ts` exercises cursor/unchanged reads, decrypt/DOM reuse, ciphertext-only persistence, simulated API outage and actual browser request failure, reconnect, same-day cache hydration, legacy/reset behavior, account/expiry cleanup and mobile layout in an isolated database.

The Amber browser suite also expires an opened Yesterday approval and verifies a fresh Today request can proceed.


## Public profiles and retries

`profile-reader.js` owns the shared public profile cache used by `NostrUI.loadProfile` and daily-chat sender observers. It deduplicates in-flight lookups and runs at most three profiles concurrently. Transport failures retry while a sender or dialog is observed, starting at five seconds with exponential backoff and ±20% jitter (base capped at five minutes). Offline browsers show an explicit offline state. An actual relay EOSE without a valid profile is a separate five-minute negative cache; successful values refresh after fifteen minutes. Failed refreshes retain the last successful name/photo/bio. Force refresh does not bypass failure/negative cooldowns. Published own-profile values supersede older in-flight reads.

The verified kind 0 transport observes actual WebSocket EOSE frames because `querySync` can return an empty result for both failure and absence. Relay sockets close on completion/error or after 3.5 seconds; the library import has a five-second timeout. Metadata never triggers signer approvals. Sender rows reserve a fixed-height line for loading, unavailable/retrying, offline and no-public-profile messages so delayed changes preserve scroll. Observers detach on room/account changes, expiry and removed messages; queued unobserved lookups skip network work. A single retry timer is cleared when no observers remain and suspended on page hide.

Avatar buttons open a read-only public-profile dialog with a picture, display name, plain-text bio and full npub/copy button. Native modal behavior plus explicit Tab wrapping, Escape, backdrop and close actions preserve keyboard access and restore focus to the avatar. Room/account changes close the dialog. HTTP(S) pictures reject credentials and unsafe schemes; image errors remove only the image and retain initials/icon fallback. No profile editing or private key controls appear in this dialog.

`test/profile-reader.test.ts` checks backoff/cooldowns, missing metadata, stale success, concurrency, unsubscribe cleanup, offline behavior and publish/read races. The sender browser suite additionally tests keyboard/modal focus, copy, backdrop/Escape, hostile metadata and automatic failure-to-success recovery without replacing message nodes.

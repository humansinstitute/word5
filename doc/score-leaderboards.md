# Completion scores and Top Scores

Word5 records a signed-in player's completed puzzle through `POST /api/completion`. The client signs a private Nostr kind 30078 event with schema `word5.completion.v1`. Its JSON content contains the game name, full UTC period ID, puzzle number, date, result, hard mode flag, and ordered guesses. The client sends this event only to the Word5 server and keeps it in local storage for retries. It is never passed to the relay publisher. Signed-out games remain playable but cannot enter the score board. The app automatically creates an anonymous local session key for visitors; that key is not treated as a signed-in identity. An extension, bunker, or imported nsec is required for ranked scores.

The server verifies the event signature and checks that the signed period matches its creation time and the current UTC puzzle period. It permits the previous period only for two minutes after rollover when the event was signed during that period. It checks every guess against the same answer and valid-word lists used by the game, rejects play after a correct guess, and recomputes the result and points. A signature binds a submission to a pubkey but cannot prove that the player solved the puzzle unaided. The first accepted event for a pubkey and period is immutable; a retry with the same event ID is idempotent.

The existing **Post to Nostr** button signs and publishes a separate public kind 1 share event without the guesses. After a relay confirms that post, the client sends the signed public event to `POST /api/publication`. The server checks it against the completion row and confirms the public event through its configured relays, then sets `published_at` and `public_event_id` on that row. A relay response saying the exact event already exists also counts as confirmation. A failed relay confirmation leaves the flag unset; the client retains the event locally and retries on page load. Server attestations, reposts, and GameStr events are triggered only by confirmed public posts when a server signer is configured. They never run for a private completion. Posting does not alter score, guesses, or local player statistics.

`GET /api/scores?days=1|7|21&published=true|false` ranks verified completion rows by puzzle period, counting the current UTC day and the preceding 0, 6, or 20 periods. It returns points, games, wins, and posted games per pubkey. Ties use wins, game count, then pubkey for a stable order. Top Scores in `social.html` uses this API. Duels and Top Streaks retain their relay data paths while the central score database accumulates coverage.

Startup migration adds `verified_completion`, `published_at`, and `public_event_id` to existing `game_submissions` tables. Legacy rows start with `verified_completion=0` and are excluded from Top Scores because earlier submissions did not bind guesses to the signature. A newly signed completion can upgrade a legacy row for the same player and period only when its validated result and hard mode match the old row; verified rows remain immutable. There is no Nostr backfill. The legacy `/api/leaderboard` endpoint remains for compatibility and has different, unverified semantics. The old `/api/submit` HTTP route is retired.

## Daily public score recap

The server schedules a kind 1 recap at **00:21 UTC**, 21 minutes after the daily **00:00 UTC** rollover (08:21 in Perth). It uses the full previous period ID, alongside the displayed game number and UTC date. Only verified completions with `published_at` set qualify, pending clarification of whether private completions may be publicly named. It aggregates by Nostr pubkey and uses the Top Scores ordering: points, wins, games descending, then pubkey ascending. New recaps include visible `#word5` content as well as the `t=word5` tag. The recap names up to ten actual accounts with `nostr:npub` links and matching `p` tags, and invites players to https://otherstuff.ai/word5/.

`game_score_announcements` stores the signed event before network I/O, one row per period, with status, attempt count, next attempt time and publication time. Retries and restarts resend the same event ID, so an uncertain relay acknowledgement cannot create a second Nostr post. SQLite immediate transactions serialize event creation and a one-minute claim prevents competing processes publishing concurrently. Each publish is bounded to 15 seconds; six attempts use exponential delays of 1, 2, 4, 8 and 16 minutes before terminal failure. A crashed final attempt becomes failed after its claim expires. The relay pool closes after success or timeout. Failed rows retain their signed event for inspection; an operator recovery must reuse that event rather than delete the row.

Startup catches up the latest completed game once its due time has passed, and resumes persisted pending events from older periods. It does not generate a historical backlog. An empty eligible board is recorded as skipped (`empty`) for that period. Missing signer or relays disables publication; the app uses its existing signer dependency. The timer targets the exact due time or next retry, with a one-minute retry after scheduler errors. Existing visit announcements retain their schedule and behavior. `/api/health` includes safe `scoreRecap` status, enabled flag and next wake time without keys or event content. Tests use synthetic signer keys, isolated databases and mock relay publishers.

## Daily noon rolling public leaderboard

A second kind 1 recap runs **every day at 12:00 UTC/GMT** (20:00 Perth). It ranks the current UTC puzzle period and preceding 20 periods, exactly the window and public-only ranking of `/api/scores?days=21&published=true` with a top-ten limit. Only verified rows with `published_at` set qualify. It sums points, games and wins per account, ordered by points, wins and games descending, then pubkey ascending. Content includes `#word5`, native `nostr:npub` mentions with matching `p` tags, the inclusive UTC puzzle date range, actual snapshot timestamp, points/games/wins and the play link. It explicitly says today's puzzle is still in progress; this is a snapshot, not 21 completed days.

`game_score_noon_announcements` stores one signed snapshot per current period independently of `game_score_announcements`. Startup only adds the noon table; existing daily rows, event JSON and IDs remain unchanged, including previously published daily content. Both schedules share the existing claim, timeout and six-attempt retry logic. A retry always uses its stored snapshot and event ID, even after a rollover. Completed, empty and failed rows suppress new generation for their own schedule/period.

On startup after noon, only today's noon snapshot is generated, using the actual catchup time in its label. Before noon, no missed prior noon snapshots are generated. Persisted pending events may still finish their bounded retries. Empty boards are stored as `empty` and skipped, even if scores arrive later that day. The combined scheduler wakes at the next 00:21 daily recap, 12:00 noon snapshot or persisted retry. `/api/health` exposes `scoreRecap.noon` with daily UTC schedule, 21-period window, current-period inclusion, next wake and latest period/status/attempts/publication time. It exposes no signed event content or keys.

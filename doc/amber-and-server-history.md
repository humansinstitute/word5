# Amber and server history

On Android, choose **Login → Amber (Android) → Open Amber**, approve the account in Amber, then return to Word5. Use the same Nostr account on a new phone. Set the browser used for Word5 as the default browser so Android opens the return in the same browser storage. No private key import is required.

Signing also requires **Open Amber**. Word5 never opens the signer from a timer, a background sync, or a page load. If approval was cancelled, use **Cancel**, then **Retry score / restore history** in the result dialog. Reloading also retries a locally completed score. A public post signature can be resumed by repeating the post action after returning; Word5 reuses the approved payload even if the caller regenerated its timestamp. It never reuses a signature for different content, tags, kind or identity.

The browser transport follows [NIP-55 web applications](https://github.com/nostr-protocol/nips/blob/master/55.md), [Amber's request/return implementation](https://github.com/greenart7c3/Amber/blob/master/app/src/main/java/com/greenart7c3/nostrsigner/service/IntentUtils.kt), and [Chrome's Android intent syntax](https://developer.chrome.com/docs/android/intents). Requests target `com.greenart7c3.nostrsigner`. The Android intent has query-free `nostrsigner:` data and percent-encoded string extras for `type`, `callbackUrl`, `returnType`, `compression`, `appName`, and (for signing) `current_user`. JSON question marks are serialized as `\u003f` so older browser-routing code cannot mistake event content for a query; JSON parsing restores the original content. The web callback supplies a result, rather than the native activity-result package extra, so the package is fixed to Amber. The connected public key and signer selection persist across reloads. Successful login removes the waiting panel and shows “Connected with Amber. You’re ready to play.”

Callbacks use a random request ID, a 15-minute expiry, and a fragment so signed completion guesses do not enter HTTP logs or referrers. Word5 strips the fragment, checks the active identity, and verifies every returned signed event's signature, hash and complete requested payload. Unsolicited, expired, altered and wrong-account returns retain the prior identity. Pending requests and approved signatures survive a full document reload. Existing-tab returns are resumed on hash changes, page restoration, focus and visibility. Concurrent restore calls share one operation; callbacks recheck the account and request after asynchronous module loading, so cancellation, retry or account switching cannot be overwritten by a late result. The app asks again only through an explicit button.

## Released Amber compatibility

The former query-based request fails against released Amber: [v6.6.9](https://github.com/greenart7c3/Amber/blob/v6.6.9/app/src/main/java/com/greenart7c3/nostrsigner/service/IntentUtils.kt) decodes the entire URI before splitting query parameters. The decoded `&amber-result=` inside Word5’s callback becomes a separate request parameter, so Amber appends its result to a truncated callback. [v3.4.3](https://github.com/greenart7c3/Amber/blob/v3.4.3/app/src/main/java/com/greenart7c3/nostrsigner/service/IntentUtils.kt) and [v4.0.0](https://github.com/greenart7c3/Amber/blob/v4.0.0/app/src/main/java/com/greenart7c3/nostrsigner/service/IntentUtils.kt) also depend on the browser application-ID extra to select query parsing; without it the former query-only request lacks the required native `type` extra. The [v7.0.0-pre3](https://github.com/greenart7c3/Amber/blob/v7.0.0-pre3/app/src/main/java/com/greenart7c3/nostrsigner/service/IntentUtils.kt) parser splits the raw query before decoding values, but requiring a prerelease is unnecessary.

All four inspected versions support the string-extra request, including the browser parser’s fallback to extras when data has no query. A browser caller has no native calling package, so Amber returns through `callbackUrl` by appending `Uri.encode(result)` (or the full event when `returnType=event`). Tests model those released parsing and return branches. They demonstrate concrete protocol failures; the installed Amber version and exact browser extras on a reported phone remain unverified without device diagnostics.

## Recover a missing return

If Word5 is still waiting after returning from Amber, choose **Return result manually**. Choose **Open Amber in copy mode**, approve, switch back to Word5, and use **Paste from clipboard → Use result**. If clipboard access is denied, paste into the visible text box with the keyboard. Word5 reads the clipboard only on that explicit button click.

For login, paste only the **public** `npub` or 64-character hexadecimal public key. You can also copy the public npub directly from Amber's account screen if the app handoff fails. Account selection restores public server history; it does not authorize a score or post. Never paste a secret key or recovery words. For signing, paste the complete signed event JSON. Word5 accepts it only for the saved, unexpired request, current account, exact payload (including timestamp), event hash and valid signature. Invalid manual input clears the input but leaves the request available to retry. Cancel removes the request and any unused returned signature.

Copy mode omits `callbackUrl`; stable Amber copies the public key or full event when there is no native calling package and no callback. Its native activity-result branch takes precedence when a calling package exists. Parser web classification and response routing are separate: `MainActivity.callingPackage` supplies the latter. The login UI passes the selected account's hex public key to the same `sendResult` routine. This is source evidence, not proof of a particular phone's failure.

A reload without a result, or an empty or unmatched callback, preserves the saved request for explicit recovery. Status distinguishes the missing public key from a missing signed event. **Copy connection status** exports only the asset version, fixed stage and fixed error code; it contains no account, event, guess, request token or logs. Text is displayed if clipboard writing is unavailable.

## History authority

`GET api/player-history?pubkey=<64 lowercase hex characters>` reads the server database. It combines signed public score history with verified private completions, deduplicates by absolute puzzle period, prefers verified outcomes, applies signed correction baselines, and counts subsequent completions once. Same-day corrections use the signed completion timestamp, rather than treating all completions as occurring at midnight. Streaks follow consecutive UTC puzzle periods, including puzzle-number rollover. Local fallback also compares full period IDs, and expire after a missed day. The response contains only the aggregate/restoration summary; detailed per-game rows, private event IDs, signing timestamps and guesses stay internal.

The browser replaces cached counters with this response, keeps today's server-completed game completed, and saves game state per public key. Identity changes discard neither the outgoing account's saved game nor the original pre-migration browser snapshot (`word5-legacy-state-v1`). Concurrent old-account history responses cannot overwrite the new account. If the server is unavailable, the active account's local game is kept; a signed completion remains pending for retry. The server's unique player/period constraint remains the final duplicate guard.

The archive includes historical self-signed public results and explicit corrections; those are evidence of what that identity published, not newly verified historical guesses. Restoring a streak requires the relevant records to exist in the server database. A developer database can contain less history than production. Tests using generated identities do not establish any real player's current streak.

## Scope and verification

Browser extensions, NIP-46 bunkers and existing browser sessions retain their signer paths. Direct Amber support currently covers account selection and event signing. Optional encrypted unfinished-game/preferences sync and encrypted chat require NIP-44 methods; the direct Amber adapter reports them unsupported. Use an existing NIP-44-capable extension or NIP-46 connection for those features. The redundant background kind-5555 publication is skipped for Amber, avoiding an extra signer round trip after a public score.

Run `bun run test` for the server and existing regression suite. Run the full-page browser regression with a locally installed Playwright module:

```sh
WORD5_PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs bun test/browser-amber-history.smoke.ts
```

The browser test uses a temporary in-memory server, real Nostr signatures, and isolated browser contexts. It captures the actual outgoing intent via Chromium navigation events and generates login/signature returns with the released Amber parser equivalent, rather than constructing successful callback fragments by hand. The unit protocol regression runs the actual adapter’s Open Amber handler through Android string-extra parsing and Amber equivalents for the four versions above, with and without a browser application ID, including punctuation and Unicode in signed event data. It covers forced full-document callbacks, tampering, cancellation, expired/unsolicited returns, timestamp regeneration, new-browser restoration, the next completion, duplicate reloads, conflicting cache, server outage, identity switching, and completion restoration during guess animation. It does not prove physical Android intent resolution, Amber approval UI behavior, Vanadium app-opening settings, or Android's browser selection. Those require a real-device check before production approval.

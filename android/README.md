# Word5 for Android

Native Kotlin/Compose client, package `ai.otherstuff.word5`, Android 8.0 or later. It bundles the repository's exact word lists and daily UTC puzzle algorithm; no WebView or private-key import exists. Amber (`com.greenart7c3.nostrsigner`) is the sole sign-in/signing/encryption provider.

Play offline, enable hard mode before the first guess, view statistics and explicitly share the web-format purple/orange emoji result through Android's share sheet. After finishing, **View result / Post to Nostr** remains below the board and in the menu, even after dismissing the result or returning from Social. Reopening never posts: preview and confirmation remain required. Confirmed posts keep per-account, per-puzzle status; a pending score link reuses the existing event. The header and menu also expose native Social, profile editing, donations and explicit Nostr posting. Guest and each Amber account have separate local files. Signing in does not attach a guest game to an identity. Sign out retains the account's local save. The app disables Android cloud backup and device transfer of its decrypted local cache.

On Amber sign in, allow the requested kinds 27235/30078 and NIP-44 encrypt/decrypt, remembering permissions if you want automatic backup. Launch, resume, foreground retry and accepted guesses/settings changes fetch the server before merging/uploading. Sync defaults on for a new Amber account; its menu toggle can explicitly pause/resume automatic sync. Paused local saves remain intact, and an explicit restore/retry resumes it. Without remembered permission, automatic operations report pending approval; tap the compact **Encrypted Sync** status in the menu to open Amber. Cancellation, unavailable Amber, denied permission and network errors retain the local save and permit retry. No request launches another login method. Unmatched activity results after process death are ignored; the next foreground attempt fetches again.

## Backup and privacy

The production API is `https://otherstuff.ai/word5/`. Private save content is self-encrypted with NIP-44 and signed by the account; the server stores ciphertext and the signed envelope only. The client verifies both player records and request-bound server responses against the pinned public server key. It validates schema, owner, dictionary words, hard-mode clues, periods, bounded sizes and completion structure after decryption. Encryption is checked by an exact decrypt roundtrip before upload. Private-backup HTTPS requests never carry plaintext guesses, native statistics or decrypted backups. Completed signed-in games now enqueue a separate private validation request. Foreground sync submits the durable per-account completion queue independently from encrypted backup; it never invokes publication/relay routes. Failed requests retain the original draft/signature until acknowledgement, including after UTC rollover and relaunch. Guest games never attach to a signed-in identity. Sharing uses an explicit OS share action and contains no guesses. **Post to Nostr** previews and confirms a public emoji result plus summary statistics, then uses Amber kind 1 signing and relay acknowledgement. Private validation contains ordered guesses, which never enter the public relay event. Posting links the separately persisted completion. The separate score action explains this before submission. A restored completion without guesses can link to an existing server score but cannot invent a new submission. Confirmed posts whose scoreboard link fails retain a per-account pending event for explicit retry.

A first backup imports existing signed-server aggregate totals, streak, known period outcomes and reconstructable distribution into a versioned baseline. Missing archival evidence cannot be invented; a historical correction may have totals whose full per-game distribution is unavailable. The statistics UI identifies that limitation. The baseline stays encrypted in subsequent backups. Each fetch reconciles fresh signed web history so later browser completions also appear; unexplained empty/older server history cannot reset it. Only reviewed server correction anchors can replace accepted totals. Reviewed lifetime floors may exceed recovered wins, without inventing games. Local correction proposals preserve the accepted server lifetime floor pending review.

All native completed periods retain outcome, attempts and hard-mode status. Exact guesses are retained for unfinished games and completed games from the past 30 UTC days. Older exact guesses are omitted from the remote save; complete outcomes remain so totals, distribution and streaks survive. Gzip plus base64 keeps a tested 10,000-outcome history within NIP-44's plaintext bound. Decompression is capped at 2 MB; the schema permits at most 10,000 native periods and 10,000 baseline periods. Exceeding limits fails visibly without truncating the local save or uploading a partial backup.

Writes compare the last fetched event ID atomically. Conflict triggers a new read/decrypt/merge; an unknown/failed fetch never authorizes a write. A completed server outcome is immutable, including when restored as an older archive entry; a conflicting local completion cannot improve it. A local completion supersedes unfinished server state. Unfinished branches use most accepted guesses, with a lexical tie-break. Different periods union. Preference timestamps select newer hard-mode settings. Settings ties favor server state. After three conflicts, the local state stays pending for retry. A lost successful write is safe: the next attempt fetches and compares the returned state before writing again.

Local files are private app storage but decrypted while the device is unlocked. The transport has no private diagnostic logging. Amber/Android own their separate permission and process behavior.

## Build and verification

Use JDK 21+ (Android Studio's JBR works), Android SDK platform 37.2, and the checked-in Gradle wrapper:

```sh
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
```

Run `bun run test` from the repository root for the server regressions. Android unit tests cover daily browser parity, duplicate letters/hard mode, strict schema/account validation, archive limits, legacy overlap, consuming restore/CAS/account isolation, server signature failure and offline reads. The signer double in consuming tests is disposable test infrastructure; it does not prove real Amber permissions or a physical-device roundtrip.

For a signed release set `WORD5_KEYSTORE`, `WORD5_STORE_PASSWORD`, and `WORD5_KEY_PASSWORD` in a protected environment; the alias is `word5`. Then run `./gradlew :app:assembleRelease :app:lintRelease`. Signing material must remain outside the checkout. Never use the debug certificate for publication. `tools/CertificateProof.java` emits public certificate and C1 app-key proof metadata for the release custodian; it does not provide the owner's Nostr signature or publish anything.

The Zapstore manifest deliberately has no license declaration because the repository supplies none. Before publication, review the exact APK hash/certificate, upload and verify public bytes, sign through the authorized owner's AP Vault, and verify relay admission and catalog listing. A build or simulated signer test alone is not release approval.

See [the server contract](../doc/native-android-backup.md) for deployment requirements.

## Web parity and native public flows

The web source remains the product reference. The game uses `#121213`, white WORD5, purple `#9333ea`, orange `#f97316`, grey `#3a3a3c`, and key grey `#818384`. Board tiles remain 48–58 logical pixels, square with 2px borders and 5px gaps, near the header; the countdown follows the board and keyboard stays at the bottom. Native status/navigation insets sit outside this content. Help/result/menu use custom Compose surfaces matching the DOM geometry rather than Material alert dialogs. Arimo, an openly licensed Arial-metric fallback, is bundled with its OFL notice; no proprietary system font is redistributed.

Social uses the existing public relay and HTTP contracts. Feed cards load public profiles/media; follows and challenge posts use explicit Amber signatures. Top Streaks uses aggregate rows, Top Scores supports 1/7/21 days and posted-only filtering, and comparisons use absolute puzzle periods and the existing score schedule. League reads and Week/Daily/member views are public-data operations; create/edit/leave/member-removal actions are explicit. Public profile kind 0 updates preserve unrelated metadata and upload selected images to Primal Blossom using the exact signed upload contract. No synthetic public writes are needed for automated validation.

The same Lightning address as the web app is shown as a QR and copyable address. Wallet opening is explicit; the app never initiates a payment itself. Daily chat uses the same Amber account and current server-verified completion as the web game; it is a native Compose screen, not a WebView.

Manual profile streak corrections require an informed confirmation, then Amber signs the existing kind 5555 correction. A versioned private overlay changes native current/best streaks while retaining all immutable games, played/won totals and distribution. Boundary-day coverage ensures a game completed after correction still counts. Signed owner validation, stale-snapshot checks and deterministic timestamp/event-ID merge protect corrections. A failed public publish retains the local encrypted correction and exposes an explicit retry; it never silently publishes later.

The inner save schema is now `word5.native-backup.v2`, with strict migration of legacy v1. The encrypted outer schema and server transport remain unchanged. Older clients reject v2 rather than silently dropping corrections. Debug builds use `ai.otherstuff.word5.visualreview` so review fixtures cannot overwrite the release app or its data.

See [the native action inventory](web-parity.md) for the intentional Amber/private-default differences and action contracts. Review screenshots and run-specific evidence belong in ignored handoffs, not this repository's reusable documentation.

## Native daily group chat

Chat uses one compact toolbar with the account/navigation menu, room name and date, day switch, and Refresh (Cancel while busy). Tap the room title for expiry and room details. Play and Social remain in the menu; Android Back returns to Play. This keeps the conversation and composer visible when the keyboard opens.

Open **Discuss today’s game** from the result or **Daily chat** from the menu. **See yesterday’s chat** and **See today’s chat** move between exactly two daily views. Each date-and-word room requires its own verified completion. Yesterday can be visited before finishing today; finishing today never unlocks yesterday. Yesterday’s chat is available if its result was already verified by Word5. An older private or restored result cannot submit missing historical guesses through this feature.

Signed room checks never submit guesses. A completed private game can unlock today only after the separate **Validate result and unlock chat** disclosure and confirmation: Word5 receives the original ordered guesses to validate that specific date’s result and record its score. No public Nostr post is created. Automatic encrypted backup never performs this validation. A midnight or account change during approval requires a fresh confirmation; a newer game cannot replace the confirmed one.

Chat requests remain kind 30078 `word5.chat.v1`; extended room discovery signs `includePrevious:true`. The server returns eligible current/yesterday rooms newest first, with access expiry `(period + 2) * DAY`: a room closes at the midnight after its day as yesterday. Physical server cleanup is separate, 25 hours after the puzzle ended (49 hours from its start); the extra retention hour does not permit access to the day before yesterday. Legacy native 6 callers without the opt-in keep their single current room and original 24-hour expiry.

The server supplies a fresh shared 256-bit key per day only to that day’s finishers. AES-GCM uses the browser’s exact nonce/period/sender additional data and a fresh 96-bit IV. Only signed ciphertext messages enter chat APIs; chat events are rejected by the public relay transport. Server and room participants hold the shared key and may retain copies; this is not server-blind encryption.

Each room has independent in-memory messages, draft, receipt cursor, pending-send reconciliation, profile/result headers and scroll position. Switching never transfers a draft or applies a stale callback to the new room. A room viewed as today becomes yesterday at rollover, retaining its own state until expiry. Expired rooms and account changes wipe the corresponding keys/messages/drafts; process death clears all chat state. Nothing enters local game files, encrypted backups or publication preferences. Offline failures keep the selected room’s cached messages and draft. Definitive send rejections permit a fresh retry; uncertain acknowledgements reconcile before resend.

Foreground automatic reads use remembered native signer permission and never launch Amber; explicit Refresh/Send may request approval. Profile names and safe HTTPS photos enrich messages separately. Result badges come only from the read response’s verified `results` entries matching the selected period, with strict boolean `won` and 1–6 attempts (loss requires 6); missing metadata omits the badge, with no fallback to today’s public result. Cached profile names/photos can be reused across rooms while results remain day-scoped.

Each room’s message cache is bounded 200, scoped by account, period and room key. Optional signed `after` cursors fetch only newer receipts; reset replaces the retained window and legacy full reads reuse already-decrypted messages. Raw server receipt cursors advance even when malformed ciphertext is skipped. Removed or stale scopes cannot be hydrated by in-flight responses. No plaintext chat cache is written to disk.

`DailyChatTest` covers production-browser WebCrypto interoperability, explicit completion consent boundaries, independent room eligibility, selected-day results, per-room cache/cursor/pending isolation, exact expiry, cancellation/offline, stale reads, lost acknowledgements and definitive retries. The `src/debug` no-network/no-signer two-room review fixture uses the production navigation/conversation composables, separate drafts/results/scroll, and an optional `yesterdayOnly` intent extra. It is excluded from release manifests/APKs. Signing and Zapstore publication remain release-custodian operations.

## Android adaptive launcher icon

The manifest uses `@mipmap/ic_launcher` for both `icon` and `roundIcon`. Android 8+ selects the adaptive resource in `mipmap-anydpi-v26`, with independent full-bleed background and safe foreground layers. Earlier Android versions retain the legacy fallback. The blue background fills the mask; the existing board artwork bytes are retained and inset 29 dp on the 108 dp layer.

When updating artwork, inspect both a circle and a squircle mask over the central 72 dp of the 108 dp layers, and keep essential foreground details within the central 66 dp safe circle. Check the merged release manifest and packaged resources, then run the app’s documented release build and lint. Launcher caches may need a normal refresh after an in-place update; never uninstall or clear user data to refresh an icon.

The code8 reconciliation contract is documented in [history-reconciliation.md](../doc/history-reconciliation.md). Public score, streak, comparison and league screens consume the accepted server projection, with UTC windows and explicit public-only scope. Release readiness does not imply server activation or Zapstore publication.
